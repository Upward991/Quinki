# STUDIO — CONCORRENZA SIDECAR: 4 SOLUZIONI + PROIEZIONE WORKER THREADS

> 21 ago 2026. Problema: con ~100 sessioni che streamano insieme, il sidecar (processo unico bun, event loop single-thread) si satura: RPC in timeout, RSS ~5GB (footprint reale ~2.3GB). Ogni chat HA il suo agent loop, ma condividono 1 thread/CPU.
> Fonti: bun PR #36256 (cap CPU-bound a cores-1), Node docs "Don't Block the Event Loop", UV_THREADPOOL_SIZE=4, bun #34579 (Bun.rust.sync).

---

## 1. IL PROBLEMA IN UNA RIGA

Un solo processo bun = un solo thread. 100 agent loop async MA con lavoro sincrono intorno (contesto, tool, jsonl, hash) → l'unico thread è saturo → le RPC (anche i delete) aspettano in coda → timeout. La UI si blocca.

## 2. LE 4 SOLUZIONI

### A) WORKER THREADS — ogni chat (o gruppo) su un thread separato
- **Come**: bun `Worker` (processi separati con heap propri). Ogni worker carica la sua copia del Pi SDK.
- **Pro**: reattività totale (il thread capo gestisce solo RPC/WS); una chat pesante non blocca le altre.
- **Contro**: il Pi SDK NON è thread-safe → ogni worker ha la SUA copia del motore AI. Memoria × N worker.

### B) CAP DI CONCORRENZA (massimo N stream simultanei)
- **Come**: semaforo nel `sendMessage` — se ci sono N stream attivi, la nuova richiesta fa coda (la UI mostra "in coda").
- **Pro**: la saturazione è IMPOSSIBILE; la memoria scende (solo N attive, le altre deattivate dalla LRU); è ciò che fa bun (#36256) e Node (UV_THREADPOOL=4).
- **Contro**: con 100 invii in parallelo, gli ultimi aspettano (ondate).

### C) YIELD DELL'EVENT LOOP — le chat cedono il passo
- **Come**: ogni blocco di lavoro sincrono fa `await setImmediate()` → le RPC si infilano tra i blocchi.
- **Pro**: la UI/RPC restano reattive anche con 100 stream (che girano più lente).
- **Contro**: non isola le chat (condividono la CPU) — solo nessun timeout.

### D) BUN.RUST.SYNC — API futura di bun
- **Come**: thread Rust nativi + canali per JS (issue #34579, non pronta).
- **Pro**: ideale se arriva.
- **Contro**: non esiste ancora.

## 3. PROIEZIONE RAM — WORKER THREADS con 100 sessioni attive

**Assunzioni**: SDK base per worker ~90MB (come il sidecar fresco); contesto sessione ~22MB l'una (misurato: 100 sessioni = 2.2GB); main thread (RPC/WS) ~90MB.

| Scenario | RAM totale proiettata | Reattività |
|---|---|---|
| **Oggi (unico processo)** | **~2.3GB** footprint (RSS 5.2GB) | Satura a 100 |
| **Worker PER SESSIONE (100 worker)** | 100×(SDK 90MB + ctx 22MB) + main = **~11.2GB** ❌❌ | Ottima ma RAM esplode |
| **Worker POOL ×8 (cores)** | 8×90MB SDK + 100 ctx (distribuiti) + main ≈ **~2.6GB** | ✅ reattivo, RAM +0.3GB |
| **Worker POOL ×4** | 4×90MB + 100 ctx + main ≈ **~2.4GB** | ✅ reattivo, RAM ~uguale |

### Verità onesta (smentisce l'intuizione)
**I worker NON migliorano la RAM.** Il costo dominante sono i **contesti delle sessioni** (2.2GB — identici ovunque vengano eseguiti). I worker AGGIUNGONO copie del SDK (90MB × N). Quindi:
- Worker per sessione = **RAM ×5** (disastro).
- Worker pool ×4 = **~uguale** (2.4 vs 2.3GB) ma con reattività perfetta.

### Cosa RIDUCE DAVVERO la RAM
- **Cap di concorrenza (20-30)**: solo 20-30 sessioni attive alla volta → il resto deattivato dalla LRU → **footprint ~0.8-1.2GB** (meno della metà). E saturazione impossibile.
- **LRU** (già attiva): le sessioni inattive vengono deattivate → non occupano RAM.

## 4. TABELLA COMPARATIVA FINALE

| Soluzione | RAM (100 stream) | Reattività | Complessità/Rischio | Verdetto |
|---|---|---|---|---|
| Worker per sessione | **11.2GB** ❌ | Ottima | Altissimo | ❌ NO |
| Worker pool ×4-8 | 2.4-2.6GB | Buona | Alto (SDK thread-safe?) | ⚠️ non per RAM |
| **Cap concorrenza 20-30** | **0.8-1.2GB** ✅ | ✅ mai satura | Basso | ✅ **RACCOMANDATA** |
| Yield event loop | 2.3GB | ✅ UI ok | Medio | ⚠️ ok, non riduce RAM |

## 5. RACCOMANDAZIONE

1. **Cap di concorrenza (20-30 stream)** — è il fix #1: riduce RAM, rende la saturazione impossibile, costo basso, è lo standard (bun/Node).
2. **Yield event loop** — aggiunta che rende la UI reattiva anche nel caso peggiore.
3. **Worker threads** — NON per la RAM (peggiora o uguale); utile solo se un giorno servisse vero isolamento CPU con pool fisso e SDK thread-safe (futuro).

## 6. COME GESTISCONO GLI ALTRI AGENTI (OpenClaw, Claude Code, Codex, OpenCode, ChatGPT)

| Piattaforma | Architettura concorrenza | Isolamento |
|---|---|---|
| **OpenClaw** | Gateway + **Nodes** (host separati) + "Cloud Workers" per lo scaling — il gateway instrada i comandi ai nodi e **isola i fallimenti per host** | **Processi/host separati** (distribuito) |
| **Claude Code** | **1 processo per sessione** — le sessioni parallele = terminali/processi separati (worktrees per isolare i progetti) | **Processo separato per sessione** |
| **OpenAI Codex CLI** | 1 processo per sessione (threads di conversazione per host) | **Processo separato** |
| **OpenCode** | 1 processo per sessione (CLI) | **Processo separato** |
| **ChatGPT (web)** | Backend server-side massiccio, ogni conversazione = thread/request su infrastruttura multi-tenant | Server farm (scale-out) |

**Il pattern comune**: **isolamento a livello di PROCESSO** (un processo per sessione) — l'OS dà l'isolamento. Nessuno usa "thread nell'unico processo" come noi.

**Cosa significa per Quinki**: la nostra app è DIVERSA — un'unica UI che gestisce molte sessioni (non terminali separati). Quindi:
- Non possiamo fare "1 processo per sessione" (sarebbe 100 processi bun = runtime+SDK×100 = RAM enorme).
- La soluzione è il **worker pool**: N worker (es. cores = 8-16), ognuno con la SUA copia del SDK, che gestiscono le sessioni assegnate. La RAM scala con le sessioni (corretto: è il costo del lavoro), ma la UI è sempre fluida.

## 7. RIPENSAMENTO: PERCHÉ IL WORKER THREAD È LA STRADA GIUSTA (sulla base del tuo ragionamento)

Il tuo ragionamento è giusto e ribalta la priorità:
- **La RAM NON è il problema**: 10GB per 100 sessioni = POCO (oggettivamente). Su un Mac 48GB/128GB, 100-1000 sessioni a 100GB sono accettabili se sono USABILI.
- **Il problema è l'usabilità**: se 100 sessioni vanno in timeout, averle non serve. Deve poterle usare TUTTE fluidamente.
- **Il cap di concorrenza LIMITA l'uso** (fa la coda) → NON va bene per chi vuole 1000 sessioni parallele.
- **I worker threads permettono l'uso fluido** (ogni chat su un thread separato) ACCETTANDO che la RAM cresca con le sessioni (che è il costo giusto).

### PROIEZIONE RAM — WORKER POOL (rivista col tuo approccio)

| Scenario | RAM (pool ×8) | Usabilità | Giudizio |
|---|---|---|---|
| 1 sessione | ~0.2GB | fluida | ✅ |
| 20 sessioni | ~0.7GB | fluida | ✅ |
| 100 sessioni | ~2.6GB | **fluida, nessun timeout** | ✅ VA BENE (poco) |
| 1000 sessioni | ~26GB | fluida (su 128GB: ok) | ✅ per Mac Studio |

**La RAM scala con le sessioni — È CORRETTO** (è il costo del lavoro reale). La differenza chiave: **con i worker, 100-1000 sessioni si USANO** (nessun timeout). Senza, a 50+ si bloccano.

### PIANO IMPLEMENTAZIONE WORKER POOL (da fare bene, rischio alto)
1. **ThreadPool di N worker** (N = cores, config): ogni worker carica il SDK una volta e gestisce le sessioni assegnate (round-robin).
2. **Main thread**: RPC, WS, orchestrazione, state UI.
3. **Streaming**: worker → postMessage → main → WS (basso latency).
4. **File jsonl condivisi**: scritture serializzate per sessione (locks).
5. **SDK thread-safety**: il Pi SDK ha stato globale (model registry, providers) — va vendorizzato per worker (ogni worker la sua copia).
6. **Cross-session** (delegazioni, MCP): messaggi tra worker via main.
7. **Testing incrementale**: prima 2 worker, poi N, con i test Enduro.

**Rischio**: ALTO (SDK non thread-safe, file condivisi, delegazioni). **Tempistica**: settimane, da fare in fase dedicata NON ora (B0 è completo).
