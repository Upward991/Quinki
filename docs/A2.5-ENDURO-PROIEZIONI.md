## 1. PROIEZIONI MEMORIA (dati REALI misurati oggi)

| Scenario | Footprint MAIN atteso | Note |
|---|---|---|
| **Tutto deattivato (15min idle)** | **95 MB** | misurato |
| **1 chat aperta (caso NORMALE)** | **300-500 MB** | la LRU tiene il contesto della sessione usata per 15min |
| **5 sessioni attive (cap LRU)** | **400-600 MB** | tetto LRU; ognuna ~40-60MB |
| **100 sessioni esistenti (aperte a turno)** | 400-600 MB | la LRU evicta le idle → il resto NON entra in RAM |
| **100 CHE STREAMANO INSIEME** | **1.2-2.5 GB** | caso stress: la guardia streaming blocca l'eviction |
| **1000 esistenti (mai aperte)** | 95-300 MB | scan = readdir+stat, niente getHistory |

**Espert (sempre singola)**: 90-160MB a riposo · 280-350MB con `__app_expert__` aperta · 300-470MB durante un suo turno.

**Punti chiave**:
1. La memoria NON scala col numero di sessioni esistenti, solo con quelle ATTIVE (≤5, o tutte se streamano).
2. Il caso stress (100 stream insieme) è l'unico che sale a 1.5-2.5GB — è il costo del lavoro, NON un leak. Deve TORNARE a ≤110MB dopo (forceGC + stale-buffer cleanup).
3. **Niente più false "Running"**: la pulizia stale-buffer (done===true) rimuove i buffer appesi → la LRU può deattivare → memoria liberata.
